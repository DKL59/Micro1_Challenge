# Improvement Changelog

How the solution evolved, from the simple baseline through to the final result.

**How these are measured.** Three cases. Verdict agreement and schema
violations are checked by script; the other two metrics are my own judgement
against the result files.

- **Verdict agreement (out of 3)** — does the system's overall verdict match
  the verdict I recorded in CASES.md for that case. `check_results.py`
  compares each structured verdict against the `my_verdict` field in
  `cases.json` and prints the count. The baseline returns free text, so its
  verdicts cannot be parsed and were scored by hand.
- **Schema violations (count)** — `validate.py` checks every assertion
  against three mechanical rules: `status` must be one of the three permitted
  values; the `quote` must appear in the source file it names; and every
  number in `source_figure` must appear inside its own quote. It reports a
  count rather than a score, because the number of assertions varies by run.
  Rule 2 checks against the source text recorded in each run's own prompt
  rather than the files now on disk, since Iteration 2 replaced those files
  and an older run should be judged against what it was actually shown.
  Rule 3 checks numbers rather than whole strings, because the model often
  adds a descriptive gloss which is not itself a claim about the source. This
  metric was built in Iteration 4 and applied retrospectively to every
  earlier run. It overlaps with "figures traceable to a source": rule 2
  checks mechanically what that metric scores by hand. They are reported
  separately because the older metric scores all-or-nothing per case while
  this one counts every violation, and because the older one predates the
  validator — but they are not independent measures. The three rules are
  themselves tested in `test_validate.py`, which also pins four known gaps in
  them; README.md describes what those gaps do and do not affect.
- **Figures traceable to a source (out of 3)** — for a case to count, every
  figure the system reports must name the source file it came from and quote
  a line that actually appears in that file. A case with one invented number
  scores zero. This measures traceability to the supplied source file, not
  that the quoted line is itself published data. Iteration 1 records where
  those two diverged. A case in which the system reports no figures scores
  trivially, having nothing to invent — Case 2 in Iteration 1 is such a case,
  which is why the failure is recorded alongside the score rather than hidden
  by it.
- **Attribution errors caught (out of 1)** — only Case 3 contains a planted
  attribution error: a correctly quoted sector figure presented as the
  company's own. There is one opportunity to catch it, so the denominator is
  one. Read the Iteration 1 caveat before relying on that run's score.
  Iteration 2 removed the signpost from the source file and re-tested, and
  the score held; Iterations 3 and 4 held it again.

Where scoring is my own judgement it is stated as such, and it rests on three
cases. That is enough to show a difference this large and not enough to
estimate its size. I have reported it as a difference, not a percentage.

| Iteration 1 — grounding | Gave the agent the company's published figures and the deposit-rate benchmark, and required structured output: a verdict, each assertion marked verified, contradicted or not_found, with the source quote and file for every figure. Both systems answer correctly; only one can show why. The agent found "Cash dividend: 12.50%" and marked the claim's 30% as contradicted, where the baseline had accepted it. It reported the yield as 12.50 / 540.20 = 2.31% and rejected Case 3's "below book value" premise with a price-to-book of 2.96x — both taken from the source rather than guessed, though both were arithmetic already present in the file rather than performed by the agent. Then the caveats, and they are heavy. Only one of the six substantive quotes — "Cash dividend: 12.50%" — is a published figure. The other five are lines I composed, because the source files mix figures with conclusions: a deposit range synthesised from three rate cards, two conclusions about Nabil's yield, the sector-attribution paragraph, and a computed price-to-book. Two of those five are arithmetic the agent could have derived from the published figures itself; three are conclusions it read rather than reached. Case 3 is the worst instance: the agent's attribution finding quotes the sentence "That figure belongs to the sector, not to EBL, and covers a different period from EBL's 2081/82 annual results", which I had written into sources/ebl.md under a heading reading "Sector context — required for the attribution check". One quote silently drops the source's bold markers, so it is not verbatim and would fail a mechanical check. And Case 2 returned all three assertions as not_found, two with "N/A" as the quote, and cited the heading "Not yet sourced" as though it were a finding. Its summary does state that no dividend was paid in the last two fiscal years, so that evidence was read but never reached the structured output; the 84% profit fall is absent entirely. Cost: 2.9x the baseline's tokens. Iteration 2 exists to answer what this run cannot: strip the conclusions out of the sources, leaving published figures and the raw sector fact, and re-run. Both of those numbers were sitting in the source file in Iteration 1 waiting to be copied. The 1/1 now measures detection rather than retrieval. Quote provenance also changed: where Iteration 1 returned one published figure out of six, this run quotes table rows, rate-card rows and market data lines throughout. The only lines of mine it quotes are the coverage statements, used as intended — on Case 2 it marked the claimed announcement `not_found` because the file states that announcements are not included, which is the reasoning the coverage line exists to enable rather than an answer handed over. The cost was a verdict. Case 1 fell to "partly supported" because the agent marked "Bank FD is giving only 4%" as verified, quoting Nabil's "Above 5 to 10 years \| 4.00%" — one row that matches, from a range running 2.75% to 4.55% on ordinary individual deposits. It verified the number and missed the claim, which is exactly the failure Case 3 was built to test and which my own CASES.md names in one sentence: verifying a number is not the same as verifying a claim. | Iteration 3 — teaching it to compare, not match | Two rules added to the agent instruction, aimed squarely at the failure Iteration 2 exposed: where a claim compares against a benchmark that varies by tenure, category or period, do not mark it verified because one row matches — state the full range, name the specific rate being compared against, and say why; and before assessing any claim that turns on a ratio, compute it from the published figures and show the arithmetic. Sources, cases and model unchanged. The only variable is the instruction. Note the difference from Iteration 2: that change repaired a broken measurement, this one changes the system being measured. | `results/agent_v3.json` — verdict agreement 3/3 (restored, and this time earned), figures traceable to a source 3/3, attribution errors caught 1/1, schema violations 4 (up from 2), mean 20.3s (24.2 / 18.5 / 18.1) and ~5,620 tokens per case | It worked, and for the right reason. Case 1's `computed` now carries "100 * 0.125 = Rs 12.50" and "12.50 / 540.20 = 0.02314 = 2.31%" — the agent performed the arithmetic that decides the case rather than copying it from the source or skipping it. The deposit assertion reports a range of "2.75% to 5.55%" and the summary names its comparator: the yield sits below individual fixed deposit rates "that range from 2.75% to 5.55% across tenures and categories (including Nabil's 5-to-10 year normal FD rate of 4.00%)". The instruction forbade marking such a claim verified but gave it nowhere to land, and the agent returned `"status": "partly supported"` — a verdict-level value in an assertion field the schema restricts to verified, contradicted or not_found. | Iteration 4 — enforcing the schema instead of asking for it | Built `validate.py`: three mechanical rules over any structured response — permitted status, quote present in the file it names, every number in a figure present in its own quote. Wired it into `agent.py` so a failing response is sent back with its violations named, up to three attempts. Two rules stating the same requirements were also added to the instruction, so the model is told the standard before being corrected against it. | `results/agent_v4.json` — schema violations 0 (down from 4), verdict agreement 3/3, figures traceable to a source 3/3, attribution errors caught 1/1, mean 70.1s (53.5 / 82.6 / 74.3) and ~10,741 tokens per case across 5 API calls for 3 cases | The loop works, and the evidence shows it working: Case 1 came back clean first time, Cases 2 and 3 each failed once and were corrected on the second attempt. Every attempt is recorded in the result file with its own token count, so the correction is visible rather than hidden behind a clean final answer. **Correction, 30 August.** Those four violations were not violations of the rule that scores this table. `agent.py` hands the validator the source files as written; `validate.py` hands it the same files with whitespace collapsed. A quote spanning a line break fails the first and passes the second, and every rejected quote in this run spans one while every corrected one stops at one. Re-scored through the scoring path, all four recompute to zero — under the intended rule this run would have been clean on the first attempt for all three cases, at three API calls rather than five and roughly 6,844 mean tokens rather than 10,741. The 0 in this row is unaffected; it comes from the scoring path, as does every figure in that column for every run. What is affected is the claim that the model was breaking its own schema. It was breaking a stricter accidental variant of it. Recorded in DECISIONS.md, 30 August. This is also the first iteration where the runtime does something an agent does — act, evaluate the result, act again on what the evaluation found. But the claim has to be narrow. Nothing else moved, because everything else was already at ceiling: verdicts stayed 3/3, traceability 3/3, attribution 1/1. This iteration did not make the answers better. It made the citations trustworthy, which is a different thing, and the thing that was never enforced. The cost is the story: 3.5x the time and 1.9x the tokens of Iteration 3; against the baseline, 4.4x the time and 5.9x the tokens. And a methodological fault, mine. This iteration changed two things at once, the loop and the instruction, where every earlier iteration changed one — so the loop's independent contribution is unmeasured here. A control run with the new instruction and the loop disabled was attempted and destroyed before it completed: the free-tier daily quota of twenty requests ran out mid-run, and I deleted the partial file rather than setting it aside, which is exactly the mistake the overwrite guard exists to prevent. A second attempt also exhausted the quota and was renamed aside rather than deleted; it is retained as `results/agent_v5-quota-failed.json`. The control has since been run as agent_v5: same instruction, same sources, MAX_ATTEMPTS set to 1 so the validator flags but never corrects. It scores verdict agreement 3/3 and schema violations 0, identical to this run, at 20.7s and 6,373 mean tokens against 70.1s and 10,741. So the loop cost 3.4 times the time and 1.7 times the tokens and moved the scored metric by nothing. It did repair four real violations under the stricter runtime rule, which agent_v5 leaves standing. The loop improves compliance with the rule it enforces; against the rule that scores this project it changes nothing. Recorded in DECISIONS.md, 30 August. |
| Final — where it ended up | No further change. Iteration 4 is the shipped configuration: published-figures-only sources with a coverage line each, my working held separately in `notes/`, an agent instruction requiring a source quote per figure, a stated range when comparing against a varying benchmark, and computed arithmetic for any ratio the claim turns on — with every response validated against three mechanical rules and returned for correction when it fails. | `results/agent_v4.json` — schema violations 0, verdict agreement 3/3, figures traceable to a source 3/3, attribution errors caught 1/1, mean 70.1s and ~10,741 tokens per case against the baseline's 15.8s and ~1,832 | The headline is not the 3/3. The baseline also scored 3/3, on the same three cases, with no documents at all. The difference is that every figure in the final run is offered with a named source file and a quoted line, that every quote has been mechanically checked to exist in the file it names, that the attribution error is caught without the answer being planted, and that the arithmetic deciding Case 1 is performed rather than assumed. What that cost is roughly six times the tokens and four times the time of a bare model call. What it bought is an answer a user can check, and a system that checks itself before answering. The honest summary of five runs: verdict agreement never distinguished these systems and was the wrong thing to optimise; traceability and attribution did, and only became meaningful once I stopped writing the answers into the corpus the agent reads; and schema compliance was invisible until I built something to measure it, at which point it turned out three iterations had been quietly breaking their own contract. One question remains open — how much of Iteration 4's result comes from the loop rather than from the instruction that accompanied it. It has been answered. results/agent_v5.json runs the same instruction with the loop disabled and scores identically, at under a third of the time and two thirds of the tokens. The loop bought no measurable improvement in the scored metric, and repaired four violations of the stricter rule it enforces. |
